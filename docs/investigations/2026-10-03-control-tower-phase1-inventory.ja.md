# Control Tower 導入第 1 段階の棚卸しと保護対象

- 状態: 一次棚卸し済み、管理境界・撤去判断の確認を継続
- 調査期間: 2026-10-03〜2026-10-04
- 対象計画: [Control Tower の段階導入と既存環境の撤去計画](../plans/2026-10-03-control-tower-adoption.ja.md)
- 方針: [既存 Organizations を維持して Control Tower を段階導入する ADR](../adr/2026-10-03-adopt-control-tower-in-existing-organization.ja.md)

## 公開記録の範囲

利用者の再認証後、管理アカウントから実行主体を確認し、組織内のアカウントに対する読み取り調査を進めた。
コード上の定義、state の記録、サービス API の実測を区別し、主要な資産と管理基盤の保持判断を整理した。
AWS リソースの変更・削除、Terraform の実行、アカウントの新設・閉鎖は行っていない。

この文書は公開用の進捗と判断基準に限定する。実環境の資産 ID・名称、state の配置・履歴、
IAM の関係、監査・統制の詳細、費用、利用者情報はローカルの詳細記録に保持し、公開用ブランチへ含めない。
認証情報・秘密値・state 本体も公開しない。詳細記録と API の取得結果は、作業を引き継ぐ際に非公開で照合する。

## 調査した範囲

- STS による実行主体、Organizations、Control Tower、Identity Center、IAM の管理関係
- 各アカウントの有効リージョン、主要なサービスとグローバルサービスの一覧・状態
- state の最新オブジェクトとメタデータ、コード・CloudFormation・実在資産との照合
- DNS・配信基盤、データ・ログ・バックアップ・暗号鍵の依存関係と保持要件
- 利用料金と既存予算の有無

全 AWS サービスを網羅した調査ではない。取得対象外・取得エラー・一覧が空の結果を区別して記録した。
機能の動作試験、データ復元、root の復旧試験、全利用者の確認は完了していない。

## 保持判断と残課題

state・認証・組織管理、DNS・配信、監査ログ、必要性が未確定のデータやバックアップは保持する。
ここでいう保護は撤去対象から除外する判断であり、AWS に保護設定を追加したという意味ではない。
独立して削除可能と確定した資産はない。

- state の正本と書き込み元、各リソースの管理者、他プロジェクトからの依存を確定する。
- Control Tower の更新経路と既存構成への影響を確認する。
- データ・監査ログの保持期間、復旧要件、月額予算・通知先を決める。
- 新規アカウントの名称と未使用メールアドレスを確定する。
- 撤去候補ごとに利用終了、削除時の影響、復旧方法と削除後の確認方法を記録する。

これらが未確定のため、第 1 段階全体は完了扱いにしない。

## CI の修復

新設と撤去を安全に段階実行できるよう、既存 CI の変更検出と適用条件を修復する。

- 変更検出は実際の `terraform/environments/` を参照する。
- PR は base と head の共通祖先から、push は before と after の差分から対象を選ぶ。
  checkout は fetch-depth 0 で履歴を取得し、検出処理ではブランチを切り替えない。
- 共有 modules / usecases の変更は、推移的な依存の見落としを避け、全登録ルートを plan 対象にする。
  厳密な依存先だけに限定する方法ではなく、必要以上の plan が発生する場合はある。
- 文書のみの変更は対象外とする。削除・名前変更も検出し、履歴不足や不正な入力は失敗にする。
  matrix 作成の失敗も最終結果のジョブで検出する。
- 定期確認と手動実行は全登録ルートを対象にする。
- AWS に接続するジョブは、リポジトリ変数 `TERRAFORM_EXECUTION_ENABLED` が文字列 `true` の場合だけ実行する。
  未設定・それ以外の値では、認証・init・plan・apply を含むジョブ全体をスキップする。
- 実行を有効化した後も、apply は main 上の手動実行で `CHECK_DIFF=_false` を指定し、plan が差分ありの場合に限る。
  PR・push・定期実行・既定の手動確認からは apply に進まない。

実行を再開する前に、モジュール参照、state・実在資産との整合、対象ルートと plan を確認する。
plan は backend にアクセスし、ロック等を伴い得るため、読み取り専用の棚卸し手段として実行しない。
実行変数の設定や workflow の起動は、今回の調査には含めない。

[GitHub のイベント仕様](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows)、
[checkout の履歴取得設定](https://github.com/actions/checkout)に基づき、コミット単位で比較する。
ローカルの実 Git 履歴とイベントデータを使う回帰試験で検証し、AWS に接続する統合試験は実施しない。
